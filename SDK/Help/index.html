INU SDK 0.1.76

Build the operating system you mean to build.

Inu exists so an OS developer can work in normal C# while still owning the design of the boot path, kernel and userland. The SDK supplies freestanding runtime support, small replaceable source components and hardware/OS contracts; Kath composes only what the OS selects and leaves coder-owned source such as Kernel.cs under the developer's control.

Why Inu exists

Most operating-system frameworks begin by deciding the kernel architecture, boot flow and subsystem boundaries for the developer. Inu is intended to do the opposite: provide the difficult low-level substrate without making those architectural choices permanent. A project may be monolithic, microkernel, hybrid or custom; SDK components can be used, replaced, materialised and edited as the OS grows.

What the SDK should be used for

Boot

Receive and normalise the machine state handed over by firmware or a loader, retain only the capabilities the OS needs, then transfer control into the OS.

Kernel

Compose memory, scheduling, drivers, storage, graphics, networking, security and other selected mechanisms in coder-owned source rather than through a fixed hidden kernel.

Userland

Run isolated applications and commands against ordinary managed APIs while Inu handles the kernel transport beneath the public SDK surface.

How to use this Help

  1. Choose Boot, Kernel or Userland in the left column.
  2. Expand a using …; namespace to see the public SDK items available in that area.
  3. Select a type or API surface to see its public members, availability, implementation notes and examples.
  4. Use those APIs from coder-owned project source. If you need to own or replace an SDK implementation, materialise that component into the OS instead of editing a second hidden copy.

How Inu is intended to expand

The current working platform is primarily x64 with UEFI, but neither is intended to define the SDK permanently. New hardware should be added behind the same driver/capability contracts so an OS can select NVMe, AHCI, VirtIO, physical devices or future controllers without changing unrelated source. Boot support should grow beyond UEFI through independent boot capability providers; the boot contracts already identify UEFI, Limine and Multiboot2 as protocol identities, while non-UEFI boot paths still require their concrete implementations. Architecture-specific code should remain behind architecture/HAL contracts so additional targets such as Arm64 or RISC-V can be introduced without leaking x64 assumptions into generic OS code.

The same rule applies to every subsystem: add a new implementation beside an interface or capability boundary, let Kath expose it as a selectable component, and keep the OS author's composition visible in source.

Public API boundary

This Help is generated from Inu.ApiContract.json, the explicit coding surface intended for SDK users. Public implementation details that are not exported through that contract are deliberately omitted. Ring-3 programs use the documented userland APIs rather than calling the Get/Set/Event transport directly.
